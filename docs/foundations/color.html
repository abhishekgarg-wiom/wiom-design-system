4Warning / caution pairing logic

Warning and Caution are merged into a single Warning family. 0 out of 10 benchmarked design systems maintain separate Warning and Caution families. This removes the "is this warning or caution?" decision paralysis.

6Product-specific mappings

BgPartnerHeader, BookingCta, etc. — removed from foundation. The architecture separates this:

  • Tier 2 (semantic) → role-based, universal
  • Tier 3 (component, future) → application-specific

The use cases still exist. Mappings live in component specs. For reference:

  • BgPartnerHeader → color.brand.secondary #4A1535
  • BookingCta → color.brand.primary #D9008D

On the optimization question

The answer is: minimize the decision surface, not the total architecture.

  • 39 semantic tokens — the only layer designers, developers, and AI interact with
  • 33 primitives — underneath for theming, never directly used in UI
  • Component tokens (Tier 3, future) — handles product-specific mappings

A designer picks from 39 tokens. That's the decision surface. Layers underneath can be as deep as needed — they're invisible to the consumer. Same model as Material Design 3, Polaris, Carbon, and Atlassian.

Architecture

This library uses a two-tier token system — the same architecture used by Material Design 3, Polaris, Atlassian, and Carbon.

┌──────────────────────────────────────────────────┐ │ TIER 1: PRIMITIVES │ │ Raw color values. For theming only. │ │ 33 tokens. NOT used directly in UI. │ ├──────────────────────────────────────────────────┤ │ TIER 2: SEMANTIC TOKENS │ │ Role-based aliases. The only tokens exposed │ │ to designers and developers. │ │ 39 tokens across 8 groups. │ ├──────────────────────────────────────────────────┤ │ TIER 3: COMPONENT TOKENS (future) │ │ Component-specific overrides. │ │ Not in scope for Next. │ └──────────────────────────────────────────────────┘

Rule: Developers and designers use ONLY Tier 2 tokens. Tier 1 exists for theming infrastructure (e.g., dark mode swap).

Decision trees

Which text color?

Is the text on a colored fill (brand, positive, negative, info)? → Yes → color.text.on-color (#FFFFFF) Is the text on a dark neutral surface (surface.inverse, brand.secondary)? → Yes → color.text.inverse (#FAF9FC) Is the text on a light colored surface (warning.subtle)? → Yes → color.text.primary (#161021) Is the component disabled? → Yes → color.text.disabled Is it a text link? → Yes → color.text.link (hover: color.text.link-hover) Is it a heading, label, input value, or primary content? → Yes → color.text.primary Is it a description, helper, placeholder, metadata, or timestamp? → Yes → color.text.secondary

Which surface color?

Standard page, card, input, or modal background? → color.surface.base Hover tint, disabled fill, or info card? → color.surface.subtle Grouped section or alternating row? → color.surface.muted Dark or inverse context? → color.surface.inverse

Which border color?

Large container (input, card, menu: 100px+ wide)? → color.border.default Small control (checkbox, radio: 20px)? → color.border.strong Light inner separator? → color.border.subtle Brand-accented boundary or focus ring? → color.border.brand

Which interaction state?

Element is interactive and hovered? → Use {family}-hover token → Brand CTA: color.brand.primary-hover → Destructive: color.negative.primary-hover → Secondary/tertiary: color.brand.primary-tint Element is pressed/active? → Use {family}-pressed token → Brand CTA: color.brand.primary-pressed → Destructive: color.negative.primary-pressed → Secondary/tertiary: color.brand.primary-subtle Element is focused? → Focus ring: color.border.brand (#FFB2E4) → Exception: Destructive → color.negative.soft (#FFB3B9) Element is disabled? → Surface: color.surface.muted → Content: color.text.disabled

Mobile note

Brand primary (#D9008D) on white passes AA at 4.84:1 but fails AAA. For Wiom's target audience (lower-end Android, outdoor use, variable brightness), test critical small text on actual devices. Consider color.brand.primary-hover (#C00080, ~5.5:1) for small brand-colored text.

How to use this guide

  1. Identify the UI context (text, surface, border, icon, semantic feedback).
  2. Look up the token mapped to that context.
  3. Use the token — do not use raw hex values or custom colors.

If your use case is not covered here, do not invent a new color. Flag it as a gap for the design system team.

Text color decision tree

Is the text on a dark/brand fill? → Yes → color.text.inverse Is the component disabled? → Yes → color.text.disabled Is it a heading, label, input value, or primary content? → Yes → color.text.primary Is it a supporting description, secondary explanation, placeholder, hint, annotation, helper text, or metadata? → Yes → color.text.secondary

When to use default vs strong

The key rule: element size determines border weight.

  • Large containers (inputs, cards, menus: 100+ px wide) → color.border.default
  • Small controls (checkbox, radio indicators: 20 px) → color.border.strong

color.border.default (#D7D3E0) appears faint on small elements, reducing clickability signals.

14Do / Don't

Do

  • Always use a token — never pick a hex value directly.
  • Use color.text.primary for content the user must read to complete a task.
  • Use color.text.secondary for hints, supporting text, and metadata, not for important content the user must read to complete a task.
  • Use color.brand.primary only for interactive or brand-emphasis elements.
  • Use semantic colors (positive, negative, warning, info) only for their intended feedback meaning.
  • Keep disabled states consistent: 40% opacity on fills/strokes, color.text.disabled on text.
  • Use color.border.strong for small controls (20px), color.border.default for large containers.

Don't

  • Don't use color.brand.primary (#D9008D) as body text or large surface fills.
  • Don't use color.text.primary on dark/brand fills — use color.text.inverse.
  • Don't use color.negative.primary for non-error purposes (it is not a decorative red).
  • Don't use color.surface.inverse for regular product screens.
  • Don't add new colors without updating this guide and the token proposal.
  • Don't use opacity to create new unnamed color variants (except for disabled states).

Decision Log

This document records every design decision made during the V1 color system build, with rationale and references.

Decision 001: Remove effects tokens from the design system

Date: 2026-04-01

Decision: Remove effect.gold.gradient and effect.shadow.color from the V1 color token system.

Rationale: Effects are not standard color tokens. Gold gradient and shadow color do not fit the color.{family}.{role} naming convention and are special-purpose values that should be handled separately if needed in future.

Impact: Token count reduced from 62 (58 semantic + 4 effects) to 58 semantic tokens. Primitive count reduced from 35 to 33.

Decision 002: Simplify on-surface text tokens from 7 to 3

Date: 2026-04-01

Decision: Collapse 7 on-surface text tokens into 3 consolidated tokens:

  • color.text.inverse (#FAF9FC) — text on dark surfaces
  • color.text.on-color (#FFFFFF) — text on any colored fill (brand, positive, negative, info)
  • color.text.on-color-dark (#161021) — text on light colored fills (warning subtle, caution subtle)

Removed tokens:

  • color.text.on-brand (#FFFFFF) → replaced by color.text.on-color
  • color.text.on-positive (#FAF9FC) → replaced by color.text.on-color
  • color.text.on-negative (#FFFFFF) → replaced by color.text.on-color
  • color.text.on-info (#FAF9FC) → replaced by color.text.on-color
  • color.text.on-warning (#161021) → replaced by color.text.on-color-dark
  • color.text.on-caution (#161021) → replaced by color.text.on-color-dark

Rationale: The 7 per-family on-* tokens resolved to only 3 unique values (#FAF9FC, #FFFFFF, #161021). This pattern was borrowed from Material Design 3, which needs per-family tokens because its dynamic theming system can make each on-* value diverge independently. Wiom V1 does not have dynamic theming, so per-family tokens add complexity without value.

The simplified approach matches what the majority of top-10 design systems do:

  • Polaris (Shopify): Single text-on-color token for text on any colored surface
  • Carbon (IBM): Single $text-on-color token
  • Atlassian: color.text.inverse as the primary token for text on colored surfaces
  • Primer (GitHub): fgColor-onEmphasis — one token for all emphasis surfaces
  • Fluent 2 (Microsoft): colorNeutralForegroundOnBrand — minimal on-color tokens

Why #FFFFFF for on-color instead of #FAF9FC: On colored fills (brand.primary, negative.primary, etc.), maximum contrast matters more than warmth. Pure white (#FFFFFF) provides the strongest possible contrast. The off-white (#FAF9FC) is reserved for text.inverse on dark neutral surfaces where the warmer tone matches the brand palette.

Impact: Text token count reduced from 13 to 9. Total semantic token count reduced from 58 to 54.

Decision 003: Remove color.text.on-color-dark — use text.primary instead

Date: 2026-04-01

Decision: Remove color.text.on-color-dark (#161021) because it is the exact same hex value as color.text.primary (#161021). Dark text on light colored fills (warning.subtle, caution.subtle) should use color.text.primary — the token already exists and serves this purpose.

Rationale: Two tokens with identical values (#161021) create confusion. A developer would need to decide between text.primary and text.on-color-dark when the answer is always the same color. text.primary already means "primary readable text on any light background" — light colored fills like warning.subtle and caution.subtle are light backgrounds.

Impact: Text token count reduced from 9 to 8. Total semantic token count reduced from 54 to 53.

Decision 004: Simplify text hierarchy from 4 levels to 3

Date: 2026-04-01

Decision: Remove color.text.tertiary and update color.text.secondary from #352D42 to #5C5570. The text system now has 3 levels: primary (#161021), secondary (#5C5570), disabled (#A7A1B2).

Problem

The 4-level text hierarchy had a critical perceptual spacing issue. The lightness gap between text.primary (#161021, L~6%) and text.secondary (#352D42, L~17%) was only 11% — below the 15-20% minimum threshold where humans can reliably perceive a difference. On lower-end mobile screens in outdoor light, primary and secondary were indistinguishable.

Decision 005: Merge border.focus into border.brand

Date: 2026-04-01

Decision: Remove color.border.focus (#FFB2E4). Its use case (focus rings) is absorbed into color.border.brand (#FFB2E4) — same hex value, same purpose. A focus ring is a brand-accent border.

Rationale: Two tokens with identical hex values (#FFB2E4) create confusion. "Focus" is a state, "brand" is an identity — the identity-level name is more correct because it covers both focus rings AND non-focus brand borders (selected cards, promotional outlines). Polaris and Atlassian name this at the identity level, not the state level.

Impact: Border tokens reduced from 5 to 4. Total semantic tokens: 51.

Decision 007: Reduce overlay to 1 token, remove skeleton tokens

Date: 2026-04-01

Decision: Keep only color.overlay.default (rgba(22,16,33,0.50)). Remove overlay.subtle and overlay.heavy. Remove skeleton.base and skeleton.shimmer entirely.

Overlay rationale

10 out of 10 benchmarked systems use exactly 1 overlay token. No top system defines multiple overlay opacities as foundation tokens. A modal scrim is a fixed design decision — not a variable.

Skeleton rationale

Skeleton loading pattern documented in component specs: "Use surface.muted for placeholder fills, surface.subtle for shimmer highlights."

Impact: Overlay reduced from 3 to 1 token (-2). Skeleton removed entirely (-2). Total reduction: -4 tokens. Semantic tokens: 44.

Gap analysis: 12 critical findings

P0 GAP 1: No interaction state tokens

The legacy system has zero tokens for hover, pressed, active, or focus states. Every top design system includes these.

SystemApproach
Material Design 3State layers — semi-transparent overlays at 8% (hover), 12% (focus), 12% (pressed)
Polaris (Shopify)Explicit tokens: interactive-hovered, interactive-pressed, interactive-active
Carbon (IBM)Hover tokens per family: $button-primary-hover, $button-danger-hover
Lightning (Salesforce)State-specific design tokens: color-background-button-brand-hover
Primer (GitHub)bgColor-accent-emphasis + hover/active variants

Wiom's CTA button is brand/600 (#D9008D). When a user taps it on mobile, there's no defined pressed state. In a trust-heavy transactional flow (payments, plan selection), unresponsive-looking buttons erode user confidence.

P1 GAP 2: Numeric naming is ambiguous and unscalable

Token names like brand/600, neutral/300, positive/200 don't communicate purpose. A developer looking at neutral/300 (#D7D3E0) cannot know if it's meant for borders, disabled backgrounds, or surface fills — the same hex is used for all three roles in the semantic table.

Recommendation: Maintain numeric primitives as the raw palette (useful for theming) but expose only role-based tokens to consumers. This is the two-tier model used by Material 3, Polaris, and Atlassian.

P2 GAP 3: Neutral/900 and Neutral/black are duplicates

Both neutral/900 and neutral/black resolve to #161021. Same hex value, two tokens.

Recommendation: Collapse into one primitive. Let color.text.primary and color.surface.inverse both reference it — duplication should live at the semantic layer, not the primitive layer.

P0 GAP 4: Inconsistent semantic hex values across tables

Critical finding — hex mismatch between primitives and semantic usage:

TokenPrimitive palette hexSemantic table hex
negative/600 #D92130 #E01E00
warning/600 #FF8000 #FF7F00
negative/300 #FFB3B9 #FFBDB3
negative/100 #FFE5E7 #FFE9E5
negative/200 #FFCCD0 #FFD3CC

This means the semantic tables are NOT faithfully mapping to the primitive palette — 5+ semantic tokens use different hex values than their claimed primitive source. A developer building from the primitive palette will use #D92130 for error states while a designer using the semantic table will spec #E01E00.

P2 GAP 5: No overlay / scrim / elevation color

No tokens for modal overlays, bottom sheet scrims, or elevation shadows. Every Wiom transactional flow likely uses modals or bottom sheets.

P2 GAP 6: No link / interactive text color

link_label_fg maps to brand/600 (#D9008D). But there is no visited, hover, or active state for links.

P1 GAP 7: Warning has 4 stops including an unused token

Warning has 4 stops: /700, /600, /500, /200. The /500 (#FFA400) appears in the primitive palette but is NOT mapped in any semantic table. Meanwhile, other families have inconsistent scale patterns.

Recommendation: Adopt a consistent inner structure across ALL semantic families: primary / soft / subtle / tint.

P3 GAP 8: No dark mode readiness

The legacy system is light-mode only. While dark mode may not be a V1 priority, structuring tokens as aliases (semantic → primitive) now makes dark mode a token-swap later vs. a full redesign.

P2 GAP 9: No skeleton / loading state color

No token for skeleton screens or shimmer loading states. This is a critical mobile pattern, especially for Wiom's audience on variable-speed connections.

P1 GAP 10: Hardcoded component-specific tokens in the semantic layer

The semantic tables include tokens that are component-specific, not system-level: bg_partner_header, bg_selection, stroke_selection. Foundation tokens should describe roles, not screens.

P2 GAP 11: Missing contrast documentation and pairing rules

Some ratios are borderline: brand/600 (#D9008D) at 4.84:1 barely passes AA for normal text. For the Indian market with outdoor usage and lower-brightness devices, aim higher.

P1 GAP 12: Semantic table inconsistencies in the "on_*" pattern

The "on_*" text tokens are inconsistent. on_brand_text is missing entirely. on_info_text is mislabeled as "negative/white".
