Library
Why Material Symbols Rounded is the right choice for Wiom
Choosing an icon library for a design system isn't just about aesthetics. It has to work for Wiom's users, Wiom's devices, Wiom's codebase, and Wiom's team — today and three years from now. Here's the case for Material Symbols Rounded across each of those dimensions.
The 5 reasons — each one matters for Wiom specifically
1. Users already know these icons

Wiom's Tier 2/3 Indian audience spends their day inside WhatsApp, YouTube, PhonePe, Google Pay, Instagram, and JioHotstar. All of these apps use Material-family Rounded icons. When a Wiom user sees a rounded search icon, a rounded home icon, a rounded back arrow — they don't need to learn anything. The icons already mean something to them because they've tapped the same shapes hundreds of times in other apps. Any other library (Phosphor, Lucide, Font Awesome) would introduce a visual language our users have never seen. On budget devices in Tier 2/3 India, unfamiliarity doesn't register as "fresh design" — it registers as "this app feels different from everything else on my phone," which erodes trust.

2. It works correctly across Wiom's size range

Wiom uses icons at 16dp (inline indicators), 24dp (standard actions), and 48dp (hero/empty states). That's a 3× size range. With a static icon library, the same stroke weight is used at every size — so a 16dp icon looks too thick and a 48dp icon looks too thin. Material Symbols solves this with optical sizing: the stroke weight automatically adjusts based on the rendered size. At 16dp the strokes get thinner for clarity. At 48dp they get proportionally heavier for presence. This isn't a nice-to-have — it directly fixes Wiom's 16dp legibility problem on 720p budget Android screens where thick strokes at small sizes make icons look like blobs.

3. It supports Wiom's fill behavior natively

Wiom uses filled icons for selected nav tabs and active toggles (bookmark, favorite). This means we need both outlined and filled variants of the same icon, in the same Rounded style. Material Symbols has a built-in Fill axis (0 = outlined, 1 = filled) that provides this for every single icon — over 2,500 of them. No other library offers outlined→filled transitions for every icon in a single consistent family. With Phosphor or Lucide, achieving this would require maintaining separate icon sets or custom workarounds for state changes.

4. It's native to Wiom's tech stack

Wiom is an Android app built with Kotlin and Jetpack Compose. Material Symbols is Google's official icon system for Android. Every icon is available as an XML Vector Drawable — the native format for Android rendering. No conversion, no wrapper libraries, no third-party dependencies. Compare this to Phosphor (community wrapper with 3 GitHub stars, not battle-tested), Lucide (web-first, no official Android package), or Font Awesome (2MB+ font files, subscription model). Material Symbols also ships as individual drawable files, not a single massive font — which means Wiom only bundles the icons it actually uses, keeping the APK lean. The current material-icons-extended dependency adds ~30MB to build cache; Material Symbols drawables eliminate this entirely.

5. It's the only actively maintained option in the Material family

Google stopped updating Material Icons in 2022. No new icons, no bug fixes, no support. As of 2026, the official Android documentation explicitly states Material Icons is "no longer recommended for new apps" and directs developers to Material Symbols. This isn't a deprecation warning buried in release notes — it's on the main Icons documentation page. Staying on a frozen library means: no new icons when Wiom adds features (e.g., no AI-related icons, no newer communication icons), no fixes for rendering issues on newer Android versions, and a growing divergence from what Google's own apps ship. Material Symbols is actively maintained with 2,500+ icons and growing — it's the library Google uses in Google Pay, YouTube, and Android system UI.

What about Phosphor, Lucide, Font Awesome? We evaluated each. Phosphor has beautiful weights but its Android/Compose wrapper has 3 GitHub stars — not production-ready for a mass-market Indian app. Lucide is web-first with no official Android package. Font Awesome requires a subscription for Pro icons and adds 2MB+ of font files. None of them match the visual language of the apps on our users' phones. The choice isn't close.
Zero visual disruption. Material Symbols Rounded uses the same icon designs as Wiom's current Material Icons Rounded. Existing screens look identical after migration. The code change is mechanical: Icons.Rounded.Home → painterResource(R.drawable.rounded_home).

Fill behavior
Filled is default. Outlined is only for state transitions.
Wiom uses filled icons as the default. Outlined is reserved exclusively for the inactive/unselected state of interactive toggles — nav tabs and bookmark/favorite-type actions. Since these patterns are rare in Wiom, most icons across the app are filled.

One rule to remember: Filled is the default. Outlined is only used for the inactive state of interactive toggles (unselected nav tab, inactive bookmark). If an icon has no toggle state — it's filled. When in doubt, use filled.
Motion: Transition timing for outlined→filled state changes (duration, easing) will be defined in the motion foundation. The icon system defines what changes, the motion system defines how fast.

Sizing model
Glyph, container, and touch target — three different things
The #1 source of dev confusion: "should this icon be 24 or 48?" The answer is usually "24dp glyph inside a 48dp interactive container." These are separate concepts. Wiom uses 4 size tokens: 16dp (restricted), 20dp (compact), 24dp (default), 48dp (hero).
The three layers
Glyph size

The visible icon itself. What the user sees. Controlled by WiomIcon tokens: 16, 24, or 48dp.

Container size

The box the icon sits in. May include padding for visual balance. Often larger than the glyph.

Touch target

The minimum tappable area. Google requires 48dp minimum. Always ≥ container. Invisible to user.

For developers: WiomIconButton handles this automatically. It takes the glyph size token and adds the correct container padding to meet touch target minimums. You set iconSize = WiomIcon.M and the composable does the rest.

Rules
8 rules for every icon decision
1
Only approved size tokens — never hardcode dp
WiomIcon.XS, .SM, .MD, or .LG. If none fit, flag it — don't invent sizes.
2
Rounded only — always specify explicitly
Icons.Default = Filled (wrong). Always write Icons.Rounded. After migration: painterResource(R.drawable.rounded_*).
3
Filled is default. Outlined is only for toggle states.
All single-state icons are filled. Outlined is used only for the inactive state of toggles — unselected nav tab, inactive bookmark. If it doesn't toggle, it's filled.
4
Glyph ≠ container ≠ touch target
Set the glyph size via token. WiomIconButton handles container padding and touch target automatically. Don't manually size the tap area.
5
icon.xs (16dp) is restricted — like meta.xs in typography
Only inline indicators and input trailing. Minimum for tappable actions is 20dp (icon.sm).
6
Icons alone must not carry critical meaning
Status icons (error, success, warning) must always be paired with text or color. Interactive icons need contentDescription. Decorative icons set contentDescription = null. Meaningful icons must meet 3:1 contrast ratio against their background (WCAG).
7
No custom icons without design review
Brand icons: ic_wiom_*. Partner icons: ic_partner_*. Only design team can introduce new custom icons. All must be 4dp multiples.
8
Color follows semantic tokens
Use onSurface, onSurfaceVariant, primary, error, etc. Never hardcode hex colors. Brand and partner icons use Color.Unspecified.
