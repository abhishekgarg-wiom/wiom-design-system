How We Built the Next Typography System

A complete report on how we audited, benchmarked, and rebuilt the Wiom typography foundation — from 24 unstructured legacy tokens with overlapping weights to 13 clean, purpose-driven semantic tokens. This scale is calibrated for both English and Hindi, with small-size choices constrained to remain readable in Devanagari on budget Android devices.
Benchmarked against: Material Design 3 · Apple HIG · Fluent 2 · Lightning · Carbon · Polaris · Primer · Spectrum · Atlassian DS · Base Web
What is a typography foundation
Four pillars that govern every text decision
In the Wiom system, weight is the primary role signal at shared sizes: Bold anchors structure, Medium marks navigational emphasis, SemiBold distinguishes interactive labels, and Regular carries readable content. This is a calibrated system choice, not a universal rule.
Naming: type.{role}.{size}e.g. type.display.lg · type.heading.xl · type.title.lg · type.body.md · type.label.lg · type.label.sm · type.meta.xs

Why fewer tokens
Problem → Industry pattern → Wiom decision
24 tokens created decision paralysis for both humans and AI. Fewer tokens directly reduce ambiguity, speed up AI-assisted development, and lower QA cost.
Illustrative example: expected AI variance with 24 vs 13 tokens
With 24 tokens
// "Use the right font for a card title"
style = T4_16_Bold   // Run 1
style = T3_20_Medium // Run 2
style = L1_16_Bold   // Run 3
style = B1_16_Bold   // Run 4
// 4 runs, 4 different valid answers.

More options at the same size = more variance = each generation needs manual review.

With 13 tokens
// "Use the right font for a card title"
style = type.title.sm // Run 1
style = type.title.sm // Run 2
style = type.title.sm // Run 3
style = type.title.sm // Run 4
// Semantic name → consistent output.

The name alone tells AI what to pick. No system context required.

For designers

Faster decisions: 13 tokens scan in seconds. 24 require scrolling and second-guessing.

No more "which one?": Legacy had 6 tokens at 16px. Every collision forced an unresolvable decision.

For developers

Weight = meaning: At any shared size, check weight: Bold = heading/title, SemiBold = label, Regular = body.

IDE autocomplete: Type "heading" → 3 options, all correct for headings. Not 12 ambiguous T-prefixed options.

For AI workflows

Consistent generation: Semantic names map to component roles. Claude Code, Cursor, and Copilot produce much more consistent outputs when token names describe purpose.

Less review: Expected reduction in typography-related review comments when using constrained, semantic tokens.

Industry pattern: Shopify reduced their typography tokens from 24+ to ~13 (Polaris v10) and reported that typography-related questions in PRs dropped. Atlassian, Stripe, and GitHub all maintain 10–13 tokens despite much larger product surfaces.

Note on the 16px exception: 16px is the only size with 3 tokens — title.sm (Bold 700), label.lg (SemiBold 600), and body.lg (Regular 400). The 100-unit gap between title.sm and label.lg would normally violate our ≥200 rule, but buttons are isolated, contained components. They never appear inline next to card titles competing for hierarchy. The semantic distinction ("this is a button" vs "this is a card title") is what matters — and the token name handles that. The SemiBold + Medium pairing (100 gap) remains prohibited because those roles do appear inline together.

Design principles
5 rules that govern every decision
1
Weight carries role at shared sizes
In the Wiom system, weight is primarily used this way: Bold = structural heading, Medium = navigational title, SemiBold = interactive label, Regular = readable body. At 16px, three tokens coexist (title.sm Bold, label.lg SemiBold, body.lg Regular) because buttons are isolated components that don't compete inline with titles or body text.
2
Token name = purpose
type.heading.xl describes its role. T1_32_Bold does not. Figma token names match Kotlin code names exactly.
3
All line-heights 4px-grid aligned
Every LH is a 4px multiple: 16, 20, 24, 28, 32, 44, 64. Vertical rhythm stays consistent in layouts.
4
Max 2 tokens per size, ≥200 weight gap — with one exception
At most sizes, two tokens with ≥200 weight gap. At 16px, three tokens are permitted (Bold 700 / SemiBold 600 / Regular 400) because label.lg serves isolated interactive components (buttons) that never sit inline beside title.sm or body.lg.

Letter-spacing logic: Negative tracking (-0.01 to -0.02em) on display/heading sizes — tighter feels confident and saves horizontal space on mobile. Zero tracking on body — default readability, no interference. Positive tracking (+0.01 to +0.02em) on label/meta — opens up legibility at small sizes, especially critical for Devanagari glyphs at 12px and below.
Units: sp, not dp. All typography tokens use sp (scaleable pixels). This means tokens automatically scale when a user changes their Android font-size accessibility setting (Settings → Display → Font size). This is a deliberate choice — Wiom's audience includes users who rely on larger text settings. If tokens used dp instead, accessibility scaling would be ignored.

Bilingual note: This scale is calibrated for both English and Hindi. Devanagari glyphs are taller than Latin at the same pixel size. display.lg (48/64) and heading.xl (32/44) use increased line-heights to provide safe clearance for Devanagari matras on multi-line wrap. meta.xs (10px) is restricted to timestamps and tags only — it must never carry Hindi reading text. The minimum readable size for Hindi body content is 12px (body.sm).

Rules — flat reference
DO and DON'T — scannable for humans and AI
DO
✓ Always use token names, never raw px values
✓ Use weight to distinguish roles at the same size
✓ Match Figma style name to code token name exactly
✓ Test Hindi strings when verifying typography
✓ Ask "what is this text's job?" before picking a token
✓ Default to body.md for reading text if unsure
✓ Default to label.md for interactive text if unsure
✓ Migrate legacy tokens when you touch a screen
✓ Mark deprecated tokens with @Deprecated + ReplaceWith
✓ Use display.lg and heading.xl sparingly — hero and section-level only
DON'T
✗ Use heading tokens for card titles (use title.sm)
✗ Use heading tokens for buttons (use label.lg)
✗ Use title.sm for buttons (use label.lg)
✗ Use label tokens for non-interactive text
✗ Use body tokens for buttons or headings
✗ Use meta.xs for Hindi body text (minimum 12px)
✗ Use meta.xs in new contexts without approval
✗ Pair SemiBold + Medium at the same font size
✗ Use sizes outside the scale (no 11, 13, 15, 18, 22, 28)
✗ Use line-heights that aren't 4px multiples
✗ Use any font other than Noto Sans

What changes tomorrow?

For new designs

Only use the 12 active tokens. If a token isn't in the active list, it doesn't exist for new work.

For existing screens

Migrate on touch. When you edit a screen, swap legacy tokens to their new mapping. No big-bang rewrite.

For code

Keep legacy aliases in the Kotlin stylesheet temporarily. Mark them @Deprecated with ReplaceWith hints pointing to new tokens.

For QA

Verify role alignment, not just size/weight. The question is "does this text use the right role token?" not "is this 16px bold?"
